# 确认写权说明（2026-11-21 钉死，当日锁死）

## 事故根因

只读访客点“确认”仍成功，正式册多出一行，审计没有写者身份。根因：确认写口
`POST /api/bookings/confirm` 的鉴权门闸未被测试覆盖，形成“假绿”——现有用例只验
`/api/holds` 的 403，确认口零覆盖。本产品档期预订在入口处拦掉，页面与会话不重开，
库仍用本仓 `data/app.db`（夹具跑本机文件库，tmp 文件 SQLite）。

## 口径钉死（只准一种，两边不得混用）

采用 **甲路径：鉴权门闸零写入**。不引入影子表、审批代写；禁止与乙路径
（先写待审影子、审批后服务端原子落正式）混用。偏航记“确认写权偏航”并拒写。

无写权确认必须零写入；失败则零写与零审同态：

1. 未登录 → `401`，不触锁、不写库。
2. 持锁内复核写权，只读角色 → `403`：正式册零增、占位零改、档期 `booked` 零增、
   `audit_trail` 零增（无写者身份不落审计）。
3. 两人同时无写权确认同一档期 → 抢档期锁；后到者抢锁失败 `409`，**只留
   `contention_log` 争用痕**（争用痕不是审计），先到者随后 `403`。两边业务写与
   审计均为零，锁在任何出口释放，无残留。
4. 仅写者（管理员/文员）确认成功时才写 `bookings`、翻占位态、加档期已订、
   落 `booking_confirm` 审计，审计 `actor` 必为认证写者。

## 五处同态（角色 / 确认结果 / 正式册 / 对账 / 审计）

| 角色 | 确认结果 | 正式册 bookings | 对账 reconcile | 审计 audit_trail |
|------|----------|-----------------|----------------|------------------|
| 只读（先到） | 403 拒写 | 零增 | all_ok 恒真 | 零增 |
| 只读（后到） | 409 争用 | 零增 | all_ok 恒真 | 零增（仅 contention_log 一条） |
| 未登录 | 401 | 零增 | all_ok 恒真 | 零增 |
| 写者成功 | 200 | 增 1 行（带 snapshot_gen） | all_ok 恒真 | booking_confirm，actor=写者 |

## 前端约束

**禁止仅藏确认钮。** 确认按钮对只读角色保持可见可点；安全边界只在服务端门闸，
只读点击由后端 403 拒绝并在页面报错，不重开页面、不重开会话。
